# Solution Design

- Status: Draft index.
- Phase status: Planned — Phase 4 has not started.
- Owner: Project owner.

Part 1 is learner-led. After domain review, the owner drafts context/container and key sequences, compares viable transaction/concurrency approaches and proposes API/data contracts plus an ADR explaining trade-offs. The assistant critiques that attempt. Technology, service boundaries and distributed components are chosen only when the slice's requirements justify them. Use [Learning Plan](../01-product/LEARNING_PLAN.md) for exercises and evidence; do not automatically generate all designs before the learner attempts them.

This directory will contain C4 views, data/API/security designs, integration/deployment plans, and architecture decisions derived from requirements and domain analysis. No framework, database, service boundaries, or API contracts have been selected.

UX flows/wireframes/prototypes will live in `UX/` when needed. Provisional UX and feasibility experiments may inform discovery and Draft requirements; label assumptions and unresolved OQ links. Committed solution contracts require readiness for the selected slice. Planned status does not prohibit early exploration and does not imply any design decision is accepted.

[ADR/](ADR/README.md) holds architecture decisions when Phase 4 begins. See the [phase gates](../PRODUCT_DEVELOPMENT_PROCESS.md).
